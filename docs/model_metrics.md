### Sender history is sparse

- 6,353,307 unique senders for 6,362,620 transactions.
- Only 9,298 senders appear more than once (at most 3 times). They account for 0.29% of rows.
- 100.00% of transactions are the first payment from that sender to that payee.

So PaySim has effectively no per-customer history. Consequences:

- "First payment from this sender to this payee" is computed but **not used as a model input**: it has the same value on every row and cannot carry signal.
- No sender-behaviour features (usual amount, usual payees, usual hours) can be learned from this data.
- Phase 3 adds a **synthetic customer-profile layer** for the demo customers (usual payees, typical amount range), clearly labelled synthetic. It gives the investigation agent customer context; it is not an input to this model.

Payees do repeat (6,362,620 transactions go to far fewer payee accounts), so the payee (mule) features are real.

## Leakage controls

- `newbalanceOrig`, `newbalanceDest` and `isFlaggedFraud` are never loaded. The first two are balances after the transaction; the third is the simulator's own rule output.
- Only pre-transaction values are used: `oldbalanceOrg` and `oldbalanceDest` are balances before the payment.
- Payee history counts only transactions from **strictly earlier steps**. The order of transactions inside one step is unknown, so same-hour transactions are treated as not yet visible.
- The split is by time. No resampling was done before or after the split; class imbalance is handled with `scale_pos_weight` computed on the training set only.
- Tier thresholds were chosen on the validation set, then reported on the test set.

## Handling of transaction types

Fraud occurs only in TRANSFER and CASH_OUT. The model is trained and evaluated on those two types only.

- PAYMENT, CASH_IN and DEBIT have zero fraud labels, so a model can learn nothing about them except "this type is never fraud". Including them would add 3.6 million trivially easy negatives and inflate every metric.
- At scoring time those types are out of the model's scope and the rule engine assigns them the Low tier. This is a property of the dataset, not a claim that such payments are safe in real life, and it is the first thing to revisit with real data.
- They are still used as history: payee inflow features count PAYMENT and DEBIT as well as TRANSFER and CASH_OUT. CASH_IN is not counted because the money flows to the originator, not to `nameDest`.

## Proposed risk tiers

| Tier | Score range | Action (decided by the rule engine) |
|---|---|---|
| Low | below 0.01 | Allow |
| Medium | 0.01 to below 0.71 | Ask the customer to verify |
| High | 0.71 to below 0.94 | Hold, create case, start customer chat |
| Critical | 0.94 and above | Hold, escalate to analyst |

How they were chosen (on validation data):

Each threshold is the lowest score at which precision on the validation set reaches a target. The more an action costs a genuine customer, the higher the target.

- **Medium (0.01)**: at least 25% of flagged payments are fraud. A verification prompt is cheap, so this tier buys recall. On validation, payments at or above this score number 872 (0.33% of payments) and include 100.0% of fraud.
- **High (0.71)**: at least 50%. Holding a payment inconveniences a genuine customer, so at least half of holds should be real fraud. On validation, 595 payments score this high and include 96.8% of fraud. This is also the volume sent to Gemini, which keeps calls within the free-tier rate limit.
- **Critical (0.94)**: at least 95%. Analyst time is the scarcest resource, so direct escalation is reserved for near-certain cases. On validation, 266 payments score this high and include 81.4% of fraud.

Validation has the lowest fraud rate of the three sets, so these precision figures are conservative; precision on the test set is higher (table below).

Result on the test set:

The score is not a calibrated probability: `scale_pos_weight` pushes scores upward. It is used as a ranking score with these thresholds.

### Choice of `scale_pos_weight`

The usual default is negatives / positives (535 here). We use its square root (23.1).

| Setting | Test PR-AUC | Test ROC-AUC | Precision at score >= 0.90 | Precision at score >= 0.99 |
|---|---:|---:|---:|---:|
| Full ratio (535) | 0.9838 | 0.9997 | 80.6% | 94.4% |
| Square root (23.1), used | 0.9845 | 0.9998 | 97.4% | 99.1% |

Ranking quality is the same, but the full ratio squeezes nearly every flagged payment above 0.99, so tier thresholds would all sit between 0.99 and 1.00. The square root spreads scores out enough to separate tiers.

## Caveats

1. **PaySim fraud is formulaic.** 97.8% of fraudulent payments move exactly the sender's whole balance; 0.0% of genuine ones do. The model mostly learns that one pattern, which is why the scores are so high. Real fraud is not this clean.
2. **Robustness check.** Retrained without the two sender-balance features (`amount_to_balance_ratio`, `sender_balance_before`), test PR-AUC falls to 0.5810 and ROC-AUC to 0.9459. That gap is how much of the performance rests on the balance pattern.
3. **This model cannot see scams.** A coached victim making an authorised payment looks genuine on every feature here, and PaySim has no such labels. That gap is what the customer protection chat (Phase 5) is for.
4. **The fraud rate shifts over time** (see above), so precision at a threshold depends on the period. Thresholds should be re-tuned on recent data in production.
5. **No customer history** in the data (see above), so no behavioural features.
